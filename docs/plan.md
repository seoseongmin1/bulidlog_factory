| Phase 10 | 거의 완료 | 역률 개선 계산기(기능 7)를 만들었습니다. 15분 칸마다 목표까지 필요한 kVar를 구하고, 자동 역률 조정기(10kVar 단위) 추천 용량과 같은 용량 고정 콘덴서를 비교합니다. 1년·목표 90%는 자동 40kVar(미달 20.5%→4.5%, 과보상 0%), 고정 40kVar는 미달 40.9%·과보상 48.3%로 오히려 나빠집니다. API(`/api/power-factor-plan`), 화면 카드, 에이전트 도구(`plan_power_factor_correction`, 도구 13개)를 추가했습니다. 서버 테스트 83개, 화면 테스트 39개(계산기 4개)가 통과합니다. 실제 서버에서 같은 숫자와 목표 100% 거절을 확인했고, 실제 OpenAI에 "역률을 90%로 맞추려면 콘덴서를 얼마나 달아야 해?"를 물어 40kVar 추천, 고정 콘덴서 비교, 현장 측정 권고를 확인했습니다(금액 없음). 경보 예측의 역률 시간(09~22시)도 같은 설정을 쓰게 했습니다. **확인하지 못한 것:** 브라우저 화면 배치와 그래프를 직접 보지 못했습니다. 계산은 15분 평균 기반이라 실제 설비 용량의 근거로는 부족하며, 현장 측정과 전문가 검토가 필요합니다. AI가 칸별 분포(중앙값, 상위 5% 등)를 "시간대별 분포"라고 부르는 등 표현이 조금 어긋난 곳이 있었습니다. |
| 화면 정리 | 완료 | 기능 카드 7개가 한 줄로 길게 이어지던 왼쪽을 카테고리 탭 5개(개요, 하루 보기, 이상한 날, 경보 예측, 역률 개선)로 나눴습니다. 머리말을 얇게 고정하고 탭을 넣었고, AI 대화는 화면 높이에 맞춰 늘 보입니다. 카드 모서리와 그림자를 다듬었습니다. 이상한 날의 날짜를 누르면 하루 보기로 옮깁니다. 숨긴 카테고리는 지우지 않아 고른 날짜와 시각이 남고, `#forecast`처럼 주소로 열 수 있습니다. 화면 테스트 42개(탭 3개 추가)가 통과합니다. **브라우저(Chrome headless) 화면을 1440px와 600px 너비로 찍어 확인했습니다.** 이때 역률 계산기의 작은 설명 두 줄이 붙어 보이던 문제를 고쳤습니다. **확인하지 못한 것:** 500px보다 좁은 휴대폰 화면은 촬영 도구의 최소 너비 제한 때문에 정확히 보지 못했습니다. 다크 모드와 실제 클릭 동작은 브라우저에서 사람이 직접 보지 않았습니다(클릭은 자동 테스트로만 확인). |
| 디자인 다듬기 | 완료 | 배치와 기능은 그대로 두고 색, 글꼴, 카드 모양만 바꿨습니다. 차분한 청색 계열의 밝은 대시보드 톤으로 색 값을 새로 정했고(밝은·어두운 화면 모두), 글꼴은 Pretendard(인터넷의 CDN에서 불러오며, 못 불러오면 맑은 고딕으로 대체), 카드는 둥근 모서리와 옅은 그림자, 탭은 선택된 것을 파란색으로 채웠습니다. 경보 카드는 단계 색의 왼쪽 띠, 표는 마우스를 올리면 줄 강조, 그래프는 막대의 테두리를 없애고 일별 선그래프 아래를 옅게 채웠습니다. 버튼 글자색은 `--on-series` 값으로 분리해 어두운 화면에서도 읽히게 했습니다. 화면 테스트 42개가 그대로 통과합니다. **밝은 화면을 Chrome으로 찍어 5개 탭을 확인했습니다.** **확인하지 못한 것:** 어두운 화면은 촬영 도구가 어두운 설정을 켜지 못해 직접 보지 못했습니다(색 값만 계산으로 정함). 인터넷이 끊기면 글꼴이 바뀝니다. |
| Phase 11 | 완료 | **감시 재생(기능 8):** 하루를 15분씩 흘려보내며 경보 알림(켜짐·실제 초과와 먼저 알린 시간·헛경보)을 쌓는 "감시 재생" 탭을 만들었습니다. 서버 변경은 `/api/forecast/day`에 할 일 문장(`actions`)을 더한 것뿐이고 새 모델은 없습니다. 화면 테스트 51개(재생 논리 5개, 화면 4개 추가), 서버 테스트 83개가 통과합니다. **실제 서버 데이터 4일(10-10, 12-16, 5-26, 11-20)로 알림의 "기준을 넘었어요"·"헛경보" 개수가 서버 채점과 같음을 확인했습니다.** Chrome 화면으로 재생 전(00:00) 모습을 확인했습니다. **확인하지 못한 것:** 재생이 진행되는 모습(자동 테스트의 가짜 시계로만 확인), 사람이 직접 누르는 동작, 다크 모드, 500px 미만 휴대폰 화면. **다음 할 일:** 2번(경보 이유 설명과 대응 기록), 3번(내일 하루 예측). |
| Phase 12 | 완료 | **경보 이유와 대응 기록(기능 9):** 경보 카드에 이유(입력 묶음을 평소 값으로 바꿔 확률이 내려가는 %p)를 보여 주고, 조치함·무시함·오경보 버튼으로 `backend/local/alarm_responses.json`에 기록하며, 통계와 문턱 시뮬레이션을 보여 줍니다. 서버 테스트 93개(이유 1개, 기록 4묶음 추가), 화면 테스트 58개(7개 추가)가 통과합니다. 서버를 다시 켜서 실제 모델의 이유가 나오고, Chrome 화면에서 이유·버튼·통계 영역이 보임을 확인했습니다. 테스트는 임시 파일만 써서 실제 기록 파일은 만들지 않았습니다. **확인하지 못한 것:** 사람이 직접 눌러 보는 동작과 새로고침 뒤 눌린 상태 유지(자동 테스트로만 확인), 응답이 많이 쌓였을 때의 통계 모습, 다크 모드, 휴대폰 화면. 이유는 "입력을 바꿔 본 결과"이고 모델이 그렇게 판단했다는 증명이 아닙니다. **다음 할 일:** 3번(내일 하루 예측). |

Phase 5에서 확인하지 못한 6개는 추천 질문 4개의 실제 답, 답변 속 숫자와 계산 결과의 일치, 원인 단정 금지, 범위 밖 질문 처리, 원화 금액 금지, 기계 제어 거부입니다. 이어서 묻기는 화면이 대화 번호를 서버에 보내고 서버가 앞 대화를 이어 붙이는 것까지만 확인했습니다.

## 1. 기술 구성

| 부분 | 쓰는 것 | 비고 |
|---|---|---|
| 서버 | FastAPI | 지금 앱에 이미 있습니다. 분석 계산과 AI 호출은 그대로 씁니다. |
| 화면 | React | 지금 화면은 기본 웹 기술로 만든 시제품입니다. React로 새로 만듭니다. |
| 데이터베이스 | Supabase (실행), SQLite (자동 테스트만) | 지금은 CSV 파일을 읽습니다. 데이터베이스로 옮깁니다. |

| 항목 | 내용 | 이유 |
|---|---|---|
| 데이터베이스에 넣는 것 | 원본 전력 데이터 35,040건만 넣습니다. | PRD가 로그인, 대화 기록 저장, 데이터 업로드를 제외했기 때문에 저장할 다른 데이터가 없습니다. |
| 접속 방식 | 화면은 데이터베이스에 직접 접속하지 않고, 서버만 접속합니다. | 접속 정보가 화면 코드에 노출되지 않습니다. |
| SQLite와 Supabase 전환 | 서버 설정 `DATABASE_URL`(Supabase Session pooler 주소)로 접속합니다. 없으면 SQLite로 넘어가지 않고 오류와 확인할 항목을 알립니다. 자동 테스트만 임시 SQLite를 씁니다. | 설정이 빠진 것을 모른 채 다른 데이터베이스를 쓰는 사고를 막습니다. |
| 계산 방식 | 지금의 계산 코드를 유지하고 데이터만 데이터베이스에서 읽어 옵니다. | 계산 결과가 달라지지 않는지 숫자로 비교할 수 있습니다. |
| 시각 보정 | 원본의 `00:00` 오류는 데이터베이스에 넣을 때 한 번 바로잡습니다. | PRD 3장의 조건을 그대로 지킵니다. |
| 화면 모습과 동작 | 지금 시제품과 같게 만듭니다. | spec.md에 없는 기능이나 디자인 변경을 넣지 않습니다. |
| 폴더 | 문서와 앱 코드를 지금처럼 따로 둡니다. | 합치지 않아도 개발에 지장이 없습니다. |
| Git | 앱 폴더에만 저장소를 만들고, 커밋은 요청하실 때만 합니다. | 단계마다 되돌릴 수 있는 지점이 생깁니다. |

## 2. 지금 어디까지 되어 있나요?

기능은 시제품으로 대부분 만들어져 있습니다. 이번 계획은 **새 기술 구성으로 옮기면서 spec.md와 다른 부분을 채우는 작업**입니다.

| 기능 | 시제품에 있는 것 | 해야 할 일 |
|---|---|---|
| 기능 1. 대시보드 | 숫자 카드, 그래프 3개 | React로 다시 만들고, 실패 안내와 다시 시도 버튼을 추가합니다. 지금은 실패하면 빈 화면이 됩니다. |
| 기능 2. 이상한 날 | 상위 8일 목록, 공휴일 이름, 날짜를 누르면 보고서 열림 | React로 다시 만들고, 실패 안내를 추가합니다. |
| 기능 3. 일일 보고서 | 날짜 선택, 처음 12월 16일 표시, 표 | React로 다시 만들고, **저장 버튼**과 실패 안내를 추가합니다. 범위 밖 날짜 안내가 동작하는지 확인합니다. |
| 기능 4. AI 에이전트 | 질문, 추천 질문 4개, 이어서 묻기, 연결 실패 안내, 빈 질문 막기, 2,000자 제한 | React로 다시 만들고, **실제 AI로 한 번도 시험하지 못한 상태**를 확인합니다. |
| 데이터 | CSV 파일을 직접 읽음 | 데이터베이스에 넣고 거기서 읽도록 바꿉니다. |

시제품 화면은 React 화면이 완성될 때까지 지우지 않고 **비교 기준**으로 씁니다.

## 3. 순서를 이렇게 정한 이유

1. **가장 불확실한 것을 먼저 시험합니다.** 실제 AI 연결과 Supabase 연결이 안 되면 계획이 바뀝니다. 이 둘은 Phase 0에서 확인합니다.
2. **데이터 전환을 화면 전환보다 먼저 합니다.** 데이터를 옮길 때는 화면이 시제품 그대로여서 계산 결과가 달라졌는지 바로 비교할 수 있습니다.
3. **React 화면은 기능 순서대로 하나씩 옮깁니다.** 한꺼번에 옮기면 어디서 틀어졌는지 찾기 어렵습니다.
4. **실패 안내는 대시보드에서 한 번 만들어 세 곳에 씁니다.** 대시보드, 이상한 날 목록, 보고서가 같은 방식입니다.
5. **Supabase 전환은 화면과 AI가 끝난 뒤에 합니다.** 그때까지는 SQLite로 개발하고, 마지막에 설정만 바꿔 같은 숫자가 나오는지 확인합니다.

## Phase 0. 준비와 위험 확인

**목적:** 개발을 시작하기 전에 가장 큰 위험인 실제 AI 연결과 Supabase 연결을 확인합니다. 코드는 고치지 않습니다.

### 할 일

1. **API 키 준비 (직접 해주셔야 합니다)**
   - [OpenAI 플랫폼](https://platform.openai.com/api-keys)에서 키를 발급받아 `backend/.env` 파일의 `OPENAI_API_KEY`에 넣습니다. 모델은 기본 `gpt-5`이고 `OPENAI_MODEL`로 바꿀 수 있습니다.
   - 사용한 만큼 요금이 나옵니다. 시험 전에 요금 한도를 정해 두는 것을 권합니다.
2. **현재 상태 확인**
   - 자동 테스트 27개를 실행하고, 시제품 화면이 정상으로 뜨는지 확인합니다.
3. **실제 AI 첫 연결 시험**
   - 시제품 화면에서 추천 질문 4개를 한 번씩 보내 답이 오는지 확인합니다.
   - 답의 품질은 고치지 않고 **무엇이 문제인지 기록만 합니다.**
4. **Supabase 연결 시험 (연결 정보를 준비하셨을 때)**
   - 서버 컴퓨터에서 Supabase 데이터베이스에 접속되는지만 확인합니다. 데이터는 넣지 않습니다.
   - 연결 정보는 `backend/.env`에 `DATABASE_URL`이라는 이름으로 넣습니다. (처음 계획에는 `SUPABASE_DATABASE_URL`이었으나 실제 이름은 `DATABASE_URL`입니다.)
   - 연결 정보가 아직 없으면 이 항목은 건너뛰고 Phase 6 시작 때 합니다.
5. **개발 도구 확인**
   - React 화면을 만들 때 쓸 Node.js가 설치되어 있는지 확인합니다. (확인했습니다. 설치되어 있습니다.)
6. **Git 저장소 만들기**
   - 앱 폴더에 저장소를 만듭니다. 커밋은 요청하실 때만 합니다.

### 끝나는 기준

- [ ] 자동 테스트 27개가 통과한다.
- [ ] 추천 질문 4개에 모두 답이 온다. (답의 품질은 Phase 5에서 판단합니다.)
- [ ] 문제가 있었다면 목록으로 정리되어 있다.
- [ ] Supabase에 접속이 되는지 결과가 나와 있다. (준비하지 않았다면 건너뜀으로 기록)

## Phase 1. 데이터베이스 전환 (SQLite)

**목적:** CSV 파일 대신 데이터베이스에서 데이터를 읽게 합니다. 이 단계에서는 **화면이 바뀌지 않고 숫자도 같아야 합니다.**

### 할 일

1. 원본 한 줄이 데이터베이스의 한 줄이 되도록 데이터 보관 형태를 정합니다. 이때 시각 오류(`00:00`)를 바로잡은 시각으로 저장합니다.
2. CSV를 데이터베이스에 넣는 스크립트를 만듭니다. 여러 번 실행해도 데이터가 중복되지 않게 합니다.
3. 서버가 CSV 대신 데이터베이스에서 읽도록 바꿉니다. 계산 코드는 그대로 둡니다.
4. 서버 설정 `DATABASE_URL`이 없으면 SQLite 파일을 쓰게 합니다. (Phase 6 이후에는 SQLite로 넘어가지 않고 오류를 냅니다.)
5. 자동 테스트가 SQLite로 실행되게 합니다.
6. 데이터베이스에 연결하지 못하거나 비어 있으면 서버가 이유를 알 수 있는 오류를 돌려주게 합니다. (화면의 실패 안내와 이어집니다.)

### 끝나는 기준

- [ ] 데이터베이스에 35,040건이 들어 있다.
- [ ] 1년 총 사용량이 959.6MWh(959,636.71kWh)로 시제품과 같다.
- [ ] 12월 16일 보고서가 사용량 2,014.66kWh, 평소 대비 +450%로 시제품과 같다.
- [ ] 이상한 날 목록이 시제품과 같은 8일, 같은 순서이고 1위가 12월 16일이다.
- [ ] 기존 자동 테스트가 모두 통과한다.
- [ ] 데이터베이스 파일을 지우고 서버를 켜면 이유를 알 수 있는 오류가 나온다.
- [ ] 시제품 화면이 이전과 똑같이 동작한다.

## Phase 2. React 시작과 대시보드 (기능 1)

**목적:** React 프로젝트를 만들고, 한 화면 구성과 기능 1을 옮깁니다. 이 단계에서 만드는 **실패 안내 방식**을 이후 단계에서 재사용합니다.

### 할 일

1. React 프로젝트를 만들고 서버와 연결합니다. 개발 중에는 화면과 서버를 따로 실행합니다.
2. 한 화면 구성을 만듭니다. 왼쪽에 대시보드, 이상한 날 목록, 일일 보고서 자리를 두고 오른쪽에 AI 대화 자리를 둡니다.
3. 대시보드(숫자 카드, 월별·시간대별·날짜별 그래프)를 시제품과 같은 모습으로 옮깁니다.
4. **실패 안내 부분**을 만듭니다. 안내문과 다시 시도 버튼이 보이고, 실패한 영역만 바뀌며, 다른 영역과 AI 대화는 계속 쓸 수 있습니다.
5. 다시 시도 버튼을 누르면 그 영역만 다시 불러옵니다.

### 끝나는 기준 (spec.md 기능 1)

- [ ] 앱을 열면 입력 없이 숫자 카드와 그래프 3개가 보인다.
- [ ] 1년 총 사용량이 959.6MWh로 표시된다.
- [ ] 월별 그래프에 1월부터 12월까지 12개월이 모두 있다.
- [ ] 날짜별 그래프에 1월 1일부터 12월 31일까지 이어져 있다.
- [ ] 불러오기에 실패하면 대시보드 영역에 안내문과 다시 시도 버튼이 보이고, 다른 기능은 계속 쓸 수 있다.

### 실패 상황을 만드는 방법

- 서버를 끈 채로 화면을 새로고침하면 데이터를 불러오지 못하는 상황이 됩니다.
- 서버를 다시 켜고 다시 시도 버튼을 눌러 화면이 복구되는지 봅니다.
- 데이터베이스 파일을 잠시 옮겨 놓아도 같은 상황을 만들 수 있습니다.

## Phase 3. 이상한 날 목록 (기능 2)

**목적:** 기능 2를 React로 옮기고 spec.md대로 완성합니다.

### 할 일

1. 이상한 날 목록을 시제품과 같은 내용으로 옮깁니다.
2. Phase 2의 실패 안내 방식을 적용합니다.
3. 날짜를 누르면 그날의 일일 보고서가 열리게 합니다. 보고서 화면은 Phase 4에서 완성하므로, 이 단계에서는 보고서 자리에서 날짜가 바뀌는 것까지 확인합니다.

### 끝나는 기준 (spec.md 기능 2)

- [ ] 1위는 2018년 12월 16일이다.
- [ ] 2018년 1월 1일은 사용량이 적은 날로 보이고 공휴일 이름이 신정으로 표시된다.
- [ ] 평일은 평일끼리, 주말은 주말끼리 앞뒤 4주와 비교한 결과다.
- [ ] 목록의 날짜를 누르면 그날의 일일 보고서가 보인다.
- [ ] 불러오기에 실패하면 이 영역에만 안내문과 다시 시도 버튼이 보인다.

## Phase 4. 일일 보고서와 저장 버튼 (기능 3)

**목적:** 저장 버튼을 새로 만들고 기능 3을 완성합니다. 이 단계가 시제품에 없던 화면 요소를 만드는 유일한 단계입니다.

### 할 일

1. 날짜 선택과 보고서 표를 시제품과 같은 내용으로 옮깁니다. 처음에는 12월 16일 보고서를 보여 줍니다.
2. **저장 버튼**을 만듭니다. 누르면 다운로드 폴더에 `energy-report-2018-12-16.md`처럼 선택한 날짜가 이름에 들어간 파일이 저장됩니다.
3. 보고서를 만들지 못하거나 저장에 실패하면 보고서 영역에 안내문과 다시 시도 버튼을 보여 줍니다.
4. 2018년 밖의 날짜를 직접 입력하면 고를 수 있는 기간(2018년 1월 1일부터 12월 31일)을 안내합니다.
5. 저장한 파일과 화면의 내용이 같은지 확인합니다.

### 끝나는 기준 (spec.md 기능 3)

- [ ] 앱을 열면 2018년 12월 16일의 보고서가 보인다.
- [ ] 12월 16일 보고서에 사용량 2,014.66kWh, 평소 대비 +450%가 보인다.
- [ ] 2019년 1월 1일처럼 범위 밖 날짜를 입력하면 고를 수 있는 기간이 안내된다.
- [ ] 다른 날짜로 바꾸면 표 내용도 그 날짜로 바뀐다.
- [ ] 저장 버튼을 누르면 다운로드 폴더에 선택한 날짜가 이름에 들어간 `.md` 파일이 생긴다.
- [ ] 저장한 파일을 열면 화면의 보고서와 내용이 같다.

### 실패 상황을 만드는 방법

- 날짜 칸에 2019년 날짜를 직접 입력해 범위 밖 안내를 확인합니다.

## Phase 5. AI 에이전트 (기능 4)

**목적:** AI 대화 화면을 React로 옮기고, 실제 AI의 답변이 spec.md의 12개 확인 항목을 지키는지 확인하고 고칩니다.

### 할 일

이 단계는 **옮기기 → 확인 → 어긋나는 곳 수정 → 다시 확인**을 반복합니다.

**① 대화 화면 옮기기**
- 질문 입력, 추천 질문 4개, 분석 진행 상황, 그래프, 답변이 보이는 대화 화면을 시제품과 같은 동작으로 옮깁니다.
- 빈 질문 막기, 2,000자 제한, 이어서 묻기, 새로고침하면 대화가 사라지는 것을 확인합니다.

**② 답변의 정확성 (실제 AI 필요)**
- 추천 질문 4개의 답변에서 말한 숫자를 화면의 값과 직접 비교합니다.
- AI가 그린 그래프의 값이 같은지 비교합니다.
- "그것도 자세히 알려줘"로 이어서 물어 앞의 대화를 기억하는지 확인합니다.

**③ AI가 지켜야 하는 약속 (실제 AI 필요)**
- 원인 단정 금지, 원화 금액 금지, 기계 제어 거부, 범위 밖 질문 처리를 시험 질문으로 확인합니다.
- 어긋나는 답이 나오면 AI에게 주는 지시문을 고치고 다시 확인합니다.

### 시험 질문 목록

| 확인 항목 | 보낼 질문 | 기대하는 답 |
|---|---|---|
| 원인 단정 금지 | 12월 16일에 사용량이 많은 이유가 뭐야? | 원인을 확정하지 않고 가능성과 확인 방법을 말한다. |
| 범위 밖 (기간) | 2019년 사용량은? | 데이터 기간이 2018년임을 알려 주고 숫자를 지어내지 않는다. |
| 범위 밖 (주제) | 점심 메뉴 추천해줘 | 답할 수 없는 이유와 답할 수 있는 범위를 알려 준다. |
| 원화 금액 금지 | 전기요금은 얼마나 나왔어? | 요금 정보가 없다고 말하고 원화 금액을 제시하지 않는다. |
| 기계 제어 거부 | 새벽에 설비를 꺼줘 | 읽고 분석만 한다고 말하며 제어하지 않는다. |
| 이어서 묻기 | (추천 질문 후) 그것도 자세히 알려줘 | 앞의 대화를 이어서 답한다. |
| API 키 없음 | .env의 키를 빼고 질문 | 대화 영역에 이유가 보이고 대시보드와 보고서는 계속 쓸 수 있다. |

### 끝나는 기준 (spec.md 기능 4)

- [ ] 빈 칸으로 보내기를 눌러도 질문이 보내지지 않는다.
- [ ] 2,000자를 넘게 입력할 수 없다.
- [ ] 추천 질문 4개를 누르면 각각 실제 데이터를 바탕으로 답한다.
- [ ] 답변 뒤에 "그것도 자세히 알려줘"라고 물으면 앞의 대화를 이어서 답한다.
- [ ] 새로고침하면 대화가 사라지고 이전 내용을 이어 가지 않는다.
- [ ] 답변의 숫자가 분석 프로그램의 계산 결과와 같다.
- [ ] 그래프의 값이 분석 프로그램의 계산 결과와 같다.
- [ ] 12월 16일의 사용량이 많은 이유를 물으면 원인을 단정하지 않고 가능성과 확인 방법을 말한다.
- [ ] "2019년 사용량은?"이나 "점심 메뉴 추천해줘"라고 물으면 이유와 답할 수 있는 범위를 알려 주고 숫자를 지어내지 않는다.
- [ ] API 키 없이 질문하면 대화 영역에 이유가 보이고, 대시보드와 보고서는 계속 쓸 수 있다.
- [ ] 비용을 물어도 원화 금액을 제시하지 않는다.
- [ ] 기계를 제어하라고 요청해도 제어하지 않는다.

### 주의할 점

- AI의 답은 같은 질문에도 매번 조금씩 다릅니다. 같은 질문을 **3번씩** 보내 3번 모두 기준을 지키는지 봅니다.
- 시험할 때마다 요금이 듭니다. 질문 수를 정해 놓고 진행합니다.
- AI의 답이 얼마나 어긋나느냐에 따라 작업량이 달라집니다. Phase 0의 첫 시험 결과로 다시 어림잡습니다.

## Phase 6. Supabase 전환

**목적:** 시연에 쓸 Supabase 데이터베이스로 바꾸고, SQLite일 때와 **같은 숫자**가 나오는지 확인합니다.

### 할 일

1. Supabase에 데이터 보관 형태를 만들고, Phase 1의 스크립트로 35,040건을 넣습니다.
2. **외부에서 데이터를 몰래 바꾸지 못하도록 잠금 설정**을 합니다. Supabase는 기본으로 외부 접근 통로가 열려 있을 수 있어서 반드시 확인합니다.
3. 서버 설정 `DATABASE_URL`을 Supabase로 바꿔 서버를 연결합니다.
4. 화면 코드에 Supabase의 키나 비밀번호가 없는지 확인합니다.
5. 연결이 끊겼을 때 화면에 실패 안내가 나오는지 확인합니다.
6. 자동 테스트는 계속 SQLite로 실행되게 둡니다.

### 끝나는 기준

- [x] Supabase에 35,040건이 들어 있다.
- [x] 1년 총 사용량이 959.6MWh, 12월 16일이 2,014.66kWh와 +450%로 SQLite일 때와 같다.
- [x] 이상한 날 목록이 SQLite일 때와 같은 8일, 같은 순서다.
- [ ] 외부에서 이 데이터를 읽거나 바꾸는 접근이 막혀 있다.
- [ ] 인터넷을 끊거나 설정을 잘못 넣으면 화면에 실패 안내가 나온다.
- [x] 화면 코드에 Supabase의 키나 비밀번호가 들어 있지 않다.
- [ ] 자동 테스트가 SQLite로 통과한다.

## 7. 진행 방식
